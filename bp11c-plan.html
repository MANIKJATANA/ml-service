Teacher delegation

Give each teacher their own classes — so their students and events lists open focused on the kids they actually teach, instead of the whole 800-student school. The final piece of BP11's "organizing structure."

The plain-English idea

Right now a teacher who logs in sees every student and every event in the school — one flat 800-row list. There's no notion of "these are my classes." BP11c adds that:

1 · Assign

A school admin links teachers to the classes (from BP11a) they teach. A teacher can own several classes; a class can have several teachers.

2 · Focus

When that teacher opens Students or Events, the list defaults to their classes — the kids and events they care about — with a one-tap switch to see the whole school.

3 · Tag events

An event can optionally belong to a class ("Grade 3B trip"). Untagged events ("Sports Day") stay school-wide and show up for everyone.

The gentle version. You chose focus, not lockdown: delegation is a helpful default, not a wall. A teacher can always flip to "All students / All events." That means BP11c adds no new security boundary — a teacher could already see the whole school, so there's nothing to bypass — and tenant isolation (one school never sees another) is completely unchanged.

The 3 decisions you locked

Scope chosen

Students + events. We add the optional event↔class link that BP11b deferred to here — so a focused teacher sees their classes' students and their classes' events (plus school-wide untagged events).

Assign UI chosen

Both surfaces. "Assign teachers" on a class's detail page and an editable "classes" chip on each teacher's staff row — two doors to the same link.

Strictness chosen

Focus filter only. A soft "My classes / All" default. No hard restrict switch, no new user column — the simplest, safest slice.

New table teacher_classes

CREATE TABLE teacher_classes (
  id               uuid  PRIMARY KEY,
  school_id        uuid  NOT NULL REFERENCES schools(id)         ON DELETE CASCADE,
  teacher_user_id  uuid  NOT NULL REFERENCES users(id)           ON DELETE CASCADE,
  student_group_id uuid  NOT NULL REFERENCES student_groups(id)  ON DELETE CASCADE,
  created_at       timestamptz NOT NULL,
  UNIQUE (teacher_user_id, student_group_id)   -- can't double-assign
);
-- indexes both directions: (school_id, teacher_user_id) and (school_id, student_group_id)

CASCADE on both foreign keys: delete a teacher or delete a class and the link just vanishes — no orphans, no student/teacher ever deleted as a side effect.

New column events.student_group_id

A nullable FK → student_groups, ON DELETE SET NULL — exactly like BP11b's events.category_id. Deleting a class un-tags its events, never deletes them. The class name is denormalized onto the event read model via a LEFT JOIN (like category_name), so lists show a class badge with no extra fetch.

How "focus" works (the request flow)

A teacher's list request carries a small flag mine=true (the FE sends it by default; the "All" toggle drops it). The server does the class math so a teacher with 3 classes gets the union of all three in one page:

1
Teacher opens Students → FE calls GET /v1/students?mine=true
2
Router sees the actor is a teacher + mine=true → looks up their assigned class ids from teacher_classes
3
Listing service adds a scope: student_group_id IN (my class ids) — ANDed under the existing school tenant scope
4
One bounded page comes back — only the teacher's kids. Flip to "All" (mine dropped) → the full school list, exactly as today

One deliberate asymmetry. A focused teacher's events include untagged (school-wide) events — a school assembly concerns everyone. But their students do not include un-classed students — a student who isn't in any class isn't "yours." Both are the intuitive reading; we document it.

The event↔class link

This is the piece BP11b explicitly parked here. It's small — it copies BP11b's own category machinery:

On the backend

  • events.student_group_id (nullable, SET NULL)
  • create/edit thread the class id (a foreign class → 404; can't be cleared via PATCH, same None-means-unchanged rule as category/term)
  • a class filter + the focus scope on the events list — through both the row-native and count-sort paths (the BP9 pattern)
  • the class name LEFT-JOINed onto the read model

On the frontend

  • a class <select> on the create/edit event dialogs (optional — "No class / school-wide" default)
  • a class badge on the events list + detail
  • a class filter on the events list (alongside category/term)
  • the "My classes / All" focus toggle (teachers only)

Deliberately NOT in scope

✗ Hard "restrict" lockdown

You chose focus-only. No server-enforced wall, no users restrict column. A teacher can always view all. (A future opt-in restrict is a documented follow-up.)

✗ Any ML / matching change

Cohort-scoped matching (narrowing face search to a grade) stays deferred to BP15. Classes remain organizational only — the ML matches seam is never touched.

✗ Assign at create/import time

Teachers are linked from the two management surfaces; wiring class-assignment into the create-teacher / CSV flows is a small future add (same as BP11a chose for students).

✗ Multi-class events

An event belongs to at most one class (or none = school-wide), mirroring one-class-per-student. Multi-tag is a documented future extension.
