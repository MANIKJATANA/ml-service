The problem

When the face-matcher isn't sure who's in a photo — two candidates are close, so it flags the match "needs review" — staff have to open each photo, one at a time, and confirm or reject. BP5 built that loop; but at a real event there can be 100+ ambiguous matches. Nobody clicks 100 times, so review gets skipped and the trust loop goes unused. Same story for archiving a term's worth of events and for grabbing a handful of photos — all one-at-a-time.

BP13 adds the "…to many at once" verb across three places, reusing what BP5 and BP9 already built.

The 3 decisions you locked

Scope chosen

All three — batch review + bulk event archive + multi-select photo download. One cohesive "bulk" phase.

Auto-confirm chosen

No auto-confirm. Staff tick the ones they want — no confidence-threshold one-click confirm. (The lane is still sorted by confidence so the obvious ones are up top.)

Batch reject chosen

One-click "Reject all remaining" — after confirming the good ones, clear the rest in one action. Guarded by a confirm dialog (it hides photos from students).

The event gallery already has a Needs review tab (BP5). Today each ambiguous match links out to a single photo. BP13 turns that tab into a checklist:

What each button does

  • Confirm selected — the ticked matches stand (the student keeps the photo). ✓ undoable.
  • Reject selected — the ticked matches are wrong → the photo is hidden from that student.
  • Reject all remaining — one click rejects every still-pending match in the lane (a confirm dialog first: "Hide N photos from those students?").
  • Select all — tick every loaded row (for a fast "confirm the whole page").

All of it reuses BP5

Each decision is exactly the BP5 set_verdict written to the match_corrections overlay — just applied to many pairs in one request. So a confirm/reject here behaves identically to the single-photo one (same hide-from-student gate, same undo, same "N to review" dashboard count auto-decrementing). No new table, no ML change.

Why the reject guard matters. Confirming only ever shows a student more photos — safe. But rejecting hides a photo from a student, so "Reject all remaining" always asks first ("Reject the remaining N matches? This hides those photos from those students.") — no accidental mass-hide.

2 · Bulk event archive

The events list gets row checkboxes + a bulk bar. Select several events → Archive (or Restore) them together. It's the existing per-event archive, applied to a set.

The staff event gallery's All photos tab gets a Select mode: tick the photos you want → Download N saves them as one zip — reusing the exact BP9 streaming download-all machinery (bounded memory, survives hundreds of photos, each recorded in the BP8b audit).

How it works (the whole build)

1
Batch review → one new endpoint POST /v1/events/{id}/review/batch takes a list of {media_id, student_id, verdict} and loops BP5's set_verdict (validated once against the event's matches — a pair that isn't a real match in this event is skipped, tenant-safe). "Reject all remaining" = the FE sends every pending pair with rejected.
2
Bulk archive → one new endpoint POST /v1/events/bulk-status takes {event_ids, status} and sets it on all in-school ids in one query.
3
Multi-select download → no endpoint; PhotoGrid gains a selection mode + the existing useDownloadAll(selectedIds).

Deliberately NOT in scope

✗ Auto-confirm by threshold

You chose manual multi-select — no "confirm everything ≥ X%" one-click. (The lane is confidence-sorted so it's still fast.)

✗ A cross-event review queue

Batch review stays per-event (the existing lane). One global "all pending reviews everywhere" queue is a future add.

✗ Any ML / matching change

The confidence shown is the ML's; the review threshold is ML-owned (BP5). BP13 only reads confidence + writes the backend correction overlay.

✗ Bulk student/staff ops

Bulk re-enroll already exists (BP8a/BP10 "Retry failed"); other bulk student/staff actions aren't part of this slice.
