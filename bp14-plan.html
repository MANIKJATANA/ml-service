The problem

Every dashboard we have is a point-in-time count — "340 enrolled, 47 events, 5,102 photos." That's the state, not the program. The people accountable for the program can't answer the questions they actually have:

School admin can't ask…

  • "How did distribution go this term?"
  • "How many of my 800 students have ever signed in?"
  • "Which events actually reached their audience?"
  • "Are we uploading more or fewer photos month over month?"

Platform admin (you) can't ask…

  • "Which schools adopted — and which stalled?"
  • A school that imported 800 students and enrolled zero looks identical on the estate list to a thriving one.
  • "Where's the drop-off — staff, enrollment, events, or delivery?"

BP14 adds the rate + trend + funnel framing on top of the counting machinery BP1/BP2 already built. Almost all of it is query-only — we group rows we already stamp (photos by upload date, events by term, "seen" reads vs announced). The one thing we don't record today is a sign-in, so that gets one tiny new column.

The 3 decisions you locked

Trends approach chosen

Derived from timestamps — group the rows we already have into buckets + rates. No snapshot table, no background job. (Trade-off: trends cover timestamped things like uploads & distribution; "enrolled" is shown as a current funnel, not a historical line — nobody stored yesterday's enrolled count.)

Sign-in metric chosen

Add users.last_login_at — one nullable column (migration 0016) + a one-line write on login. Powers "ever signed in" and an engagement rate at both tiers.

Scope chosen

Both tiers in one phase — the school-admin analytics page and the platform per-school adoption funnel + stalled-school flag. One decisions record (0062).

A new Analytics page (school admin + teacher, same permission as the dashboard). Three rate cards up top, a per-term table, and a simple month-by-month trend — all built from data we already have plus the new sign-in signal.

What each number means

  • Delivery rate = announced events ÷ total events (reuses BP4's "announced" = notified_at set, or auto-notify + completed).
  • Sign-in rate = students whose last_login_at is set ÷ all students.
  • Engagement = distinct students who've opened ≥1 distribution ÷ students who had one reach them (from the notification_reads BP4 already writes).
  • By term = events grouped by BP11b's term label → event count, photo count, % announced.
  • Trend = photos (and events) bucketed by month from their created_at, last ~12 months.

Reuse, don't rebuild

The counts (students/enrolled/events/photos/distributed) are the same aggregates the dashboard already runs. BP14 adds a handful of grouped queries (by term, by month, distinct-seen, signed-in count) and a pure AnalyticsService that composes them into rates — the exact BP1 pattern. No N+1: each metric is one grouped scan, zipped in Python.

2 · Estate analytics — the adoption funnel

For the platform admin: a per-school funnel (staff → students → enrolled → events → distributed) and a stalled-school flag, so a stuck school stops looking like a healthy one.

The funnel per school

Each row is the drop-off: how many staff, students, enrolled students, events, and distributed events. Enrolled-vs-total is the review's headline signal — the gap between "imported" and "enrolled" is the enrollment wall made visible.

The stalled heuristic (simple, documented)

A school is flagged when a plain rule trips — e.g. students > 0 but enrolled = 0, or 0 events created in the last 30 days. No ML, no scoring model; a transparent rule the operator can trust and we can tune.

Built from the same cross-tenant grouped aggregates the schools list already uses (counts_by_school), plus a few new ones (enrolled-per-school, distributed-per-school, signed-in-per-school, recent-activity-per-school) — each one grouped query, zipped by school_id in Python. No per-school loop.

The one new column

Migration 0016 — users.last_login_at (nullable timestamp). That's the whole schema change. On a successful login we write now() to it (one line in the auth flow — not on token refresh, which isn't an interactive sign-in). Everything else in BP14 is query-only.

Honest note: existing users show null until their next login (no backfill — we never recorded past logins, so we can't invent them). The sign-in rate climbs from launch as people log in; it's a forward-looking signal, which is the honest thing it can be.

How it works (the whole build)

1
Migration 0016 adds users.last_login_at; the login endpoint writes it on success (UserRepository.touch_last_login). Verified up→down→up on a throwaway DB.
2
New aggregates on the existing repos — grouped, tenant-scoped (and a few cross-tenant for the estate): by-term rollups, by-month upload/event counts, distinct-seen students, signed-in counts, per-school enrolled/distributed/recent-activity. Pure SQL GROUP BY, one scan each.
3
A pure AnalyticsService composes those into two value objects — SchoolAnalytics and EstateAnalytics — computing the rates in Python. No new library; the layering invariant holds (services stay import-pure).
4
Two read endpoints + two frontend pages — a school Analytics page (rate cards + term table + a dependency-free CSS bar/trend) and a platform Estate-health page (funnel table + stalled alerts), reusing StatCard.

Deliberately NOT in scope

✗ Historical snapshots / a rollup job

You chose query-only. So "enrolled students on a past date" isn't a line — it's shown as the current funnel. A snapshot table + scheduler is the documented scale-up.

✗ Outbound email / SMS delivery stats

There's no email channel yet (that's BP12). "Delivery" here = in-app announced + seen, the signals BP4 already writes — not send/bounce/open of an email.

✗ A charting library

The trend/bar visuals are plain CSS/SVG (accessible, with a table fallback) — no new frontend dependency.

✗ Login backfill / refresh-as-signin

Pre-existing users read null until their next login; token refresh doesn't count as a sign-in. The rate is forward-looking from launch.
