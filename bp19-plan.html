BP19 — Pipeline resilience & stall visibility

The second build off the Round-3 roadmap. It fixes Critical #2 — an event that can silently get stuck forever — and the "we can't see it going wrong" gaps around it.

The problem we're fixing

Today, if a batch of photos hits a snag while processing, the event can get stuck saying "Distribution is running" — forever — and nobody can tell or fix it in the app.
The chain, step by step: the worker tries a batch, hits an error it can't get past (e.g. the face-recognition index is out of date), retries 5 times, gives up, and quietly sets the job aside in a "failed jobs" bin that nothing ever reads. → The event is left marked "processing". → The screen keeps saying "Distribution is running — this updates automatically" and spins forever; the Process button is hidden while it "runs"; pressing anything is blocked with "already processing". → No button, no CLI, no signal — the only way to unstick it is editing the database by hand. The students in those photos never get them, and staff never even know something broke. On top of that: the failure side of the pipeline reports zero metrics, a slow-but-healthy event looks identical to a dead one, new photos added to a finished event go unnoticed, "All processed" is shown even when some photos failed, and a long upload has no "you're still uploading" guard.

What we're building — four slices

BP19aUnstick it — a visible "Failed" event you can retry kills Critical #2backend + worker1 migration
NowA dead job disappears into a bin nothing reads; the event spins on "Distribution is running" forever, the Process button is hidden, and the API refuses to let you try again. Only a hand-edit of the database can rescue it.
AfterA dead job flips the event to a clear "Failed" state within seconds, and a Retry button appears. As a safety net, if an event has been "running" far too long (past a set time), Process is re-enabled anyway — so even a job that vanished entirely can always be restarted. No hand-edits, ever.
How: this mirrors exactly what we already did for stuck photos (BP8a) — one small database change to allow a "failed" state on events, the worker writes that state by reading the failed-jobs bin (the "consumer" that was missing), and the "you can't press Process" rule is relaxed for a failed or long-overdue event. The one migration in this whole phase.
BP19bMeasure the failures — so alerts can actually fire reliabilityworker onlyno migration
NowWhen jobs fail, there are no numbers — just a log line that no monitor can watch. There's no count of failed jobs, no size of the failed-jobs bin, no "oldest thing still waiting" gauge, no failed-photos count. In fact the worker doesn't publish any metrics at all today.
AfterThe worker publishes real numbers a dashboard/alert can watch: failed jobs (by reason), failed photos, how many jobs are stuck in the failed bin, and how long the oldest waiting job has been waiting. Now "something is wrong" can page someone instead of hiding in the logs.
How: give the worker its own tiny metrics endpoint (it never had one — this also switches on the counters it already records but nobody could read), add the four new failure numbers, and wire the port through Docker/CI. No database change, no app-screen change.
BP19cShow the stall — age, the second batch, and failed photos visibilitybackend + frontendno migration
NowA stuck event looks identical to a healthy one ("updates automatically", no clock). If you add new photos to a finished event, the events list still says "Completed" and the dashboard doesn't nudge you. And the dashboard says "All processed" even when photos actually failed.
AfterThe event shows "Processing since 2:14 PM" and, past a threshold, "this is taking longer than usual — you can retry". The events list and dashboard notice a second batch of unprocessed photos on a finished event. And the dashboard surfaces "N photos failed processing" instead of falsely saying all is well.
How: the "processing since" time is already sent to the screen — we just show it. The list pill and the dashboard alert start counting unprocessed/failed photos the way the detail page already does. Small, mostly front-end, no database change.
BP19dDon't lose an upload in progress upload safetyfrontend onlyno migration
NowIf some files fail mid-upload, there's no "Retry failed" — you'd re-add them by hand. And if you close the tab or click away while photos are still uploading, they're gone with no warning at all.
AfterA "Retry failed (N)" button re-sends just the ones that failed, and the browser warns "you're still uploading — leave anyway?" if you try to close or navigate away mid-upload.
How: the uploader keeps hold of the failed files for a one-click retry (same pattern as the bulk-photo tool), plus a small reusable "you have work in progress" guard on the upload page. Front-end only, nothing new to install.

Build order & how we'll work

Order  BP19a → BP19b → BP19c → BP19d  — the actual unstick first (the Critical), then the numbers to watch it, then the on-screen visibility, then upload safety.
Process — you're reading step 2 now. Each slice is then built on its own, run through the full check (types + lint + tests + build) and a 2× self-review, and brought back to you to review. Nothing is committed until you say so. We do them one by one, not all at once.

How we'll prove BP19a actually works

The whole point is "no event can strand invisibly", so the key test walks exactly that:
  1. Force an event's job to fail permanently (the version-mismatch case) so it lands in the failed-jobs bin.
  2. The worker's new reader flips that event to "Failed" — it's no longer spinning "Distribution is running".
  3. The API now allows Process again (it used to reject with an error), and the screen shows a Retry button.
  4. Pressing Retry re-queues the event — once the underlying cause is fixed, it completes and the students get their photos.

Plus: the one migration is tested up-and-down on a throwaway database (never your real dev data), the worker's "mark failed" write is checked against a real Postgres, and every slice passes the full backend + frontend checks and the 2× review before it reaches you.

Not in this build (noted honestly): reaping the leftover storage objects of an event's media (a small, separate cleanup — recorded as a known minor leak), and resumable / whole-folder uploads (a bigger ask, still deferred). The rest of the Round-3 roadmap (BP20–BP25) stays as-is in product/07.
