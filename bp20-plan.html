BP20 — The arrival moment

The next Round-3 build. It makes a student's "new photos" moment actually open on the new photos, name them, and stay fresh — and gives the student's screen a warmer, calmer look.

Plan: C:\Users\…\plans\…jolly-peach.md (approved) · findings: product/06 theme L · roadmap: product/07 BP20 (+ BP20b) · this is the explainer to verify before any code · one phase, seven small pieces · frontend only — no database, no ML, no server change

The problem we're fixing

The "new photos" signal exists — and then points at nothing.
A student gets a "3 new" badge, taps "My Photos"… and the grid opens on photos from three years ago — the stream is oldest-first, and the new event is the last chip in a wall of ~60. The "new" flags are cleared the instant the page loads — before they've looked at anything — and the badge, once shown, never refreshes in a tab left open. The photos themselves say nothing (no event, no date), and "Download all" hands over photo-001…photo-900 in one pile — and on some browsers it silently keeps only the oldest 500, then tells them to "try again to get the rest" (which re-downloads the same 500). On top of all that, the whole screen wears the admin's gray sidebar chrome, not a warm receive space.
Your calls (already made): take the full scope — the moment-fix and the warm reskin (BP20b); a "new" event clears when its photos actually appear on arrival (not the instant the page loads); delivered as one phase.

What we're building — seven small pieces, one phase

1Newest first the core fixno server change
NowThe grid opens on the oldest photos; the newest event is the last chip.
AfterNewest photos and newest events first — you land on what's actually new.
How: the app just reverses the lists it already receives (the server sends them oldest-first). No server change.
2A banner that points somewhere — and clears only once you've seen it the core fix
NowA generic "New photos from 3 events" line that links nowhere — and every "new" flag is wiped the moment the page loads, before you've looked at anything.
AfterThe banner names each new event as a tap-to-filter link; the "new" marks clear once the photos are actually on screen (on arrival, not on load) — so the badge reflects what you've really seen. It's a one-visit highlight that's gone next time.
3A badge that stays fresh the core fix
NowThe "new photos" badge is fetched once when the tab opens, then freezes — a tab left open all day never lights up.
AfterThe badge refreshes when you return to the tab and gently every ~minute, so new photos actually light it up.
How: only the two "count" badges (the student's new-photos badge and the staff dashboard badge) poll gently — the rest of the app is unchanged.
4Events that fit the screen the core fix
Now~60 events render as one giant wall of pills in creation order — on a phone that's the entire first screen, pills instead of photos.
AfterA short row of chips when there are only a few events; when there are many, they group by year (newest first) with older years folded away. The date is already in the data.
5Photos that tell their story the core fix
NowOpen a photo and it says only "812 of 900" — never which event, when. (Screen readers get an empty description.)
AfterEach photo shows its event name + date in the viewer and as its description, with an optional caption on the tile.
How: the photo already knows which event it belongs to; we just look up that event's name + date (both already loaded on the page) and show them.
6A save you can actually use the core fix
Now"Download all" gives photo-001…photo-900 in one pile named my-photos.zip; on non-Chrome browsers it silently keeps only the oldest 500, and the message ("try again to get the rest") just re-downloads the same 500, then vanishes in 5 seconds.
AfterFiles are grouped + named by event and date ({event}/{date}-001.jpg), the zip is my-photos-{date}.zip, single saves are named by event; the "only got some" message is honest ("showing the first 500 — use an event filter, or Chrome, for all N") and stays on screen instead of disappearing.

How we'll check it

The full frontend gate (types + lint + build) stays green, plus a walk of the student surface:
  1. Open "My Photos" → the newest photos are on top; the newest event is the first chip.
  2. The banner names the new events and each one filters to it; the "new" clears only once the photos are on screen.
  3. Leave the tab open and come back → the badge refreshes.
  4. With many events → they group by year, newest first.
  5. Open a photo → it names its event + date.
  6. "Download all" → files named by event/date; the "only got some" message is honest and stays up.
  7. The student screen looks warm + slim; staff screens look exactly as before.

Not in this build (noted honestly): making "This isn't me" safe (a confirm + an undo) is the next phase (BP22); putting the event filter in the web address (shareable / bookmarkable) is a later floor-sweep. The "newest-first" ordering is just the app reversing lists it already receives — no server change, no database migration, no ML change. After this, the roadmap continues with BP22 (the review loop).
