BP24 — Two-way doors

The next Round-3 build. Make mistakes recoverable and batch work survive errors — so a wrong tag, a typo'd CSV, or a half-finished download is a quick fix, not a dead end.

The problem we're fixing

Several everyday actions are "one-way doors" — once you go through, there's no easy way back.
Tag an event with the wrong category or class and you can never clear it — a mis-tagged class quietly mis-scopes a teacher's lists forever, and the only true undo is to delete and re-upload the whole event. Assigning 800 imported students into ~25 classes is ~800 search-and-clicks. A CSV import with 30 typo'd emails makes you hand-retype them into a new file. The staff "Download all" can say "Downloaded 40" when only 12 saved (or none did). And the new teacher you just added doesn't show up until you reload; the "who's opened their photos?" roster is an unpaginated wall you scan by eye.
Your calls (already made): include the clearable-tags fix (it revises a locked decision, 0027 — with your sign-off); do both class-at-scale shapes (a CSV class column and a paste-emails box); and ship in two sub-phases — the backend-touching work first, then the front-end sweep.
Sub-phase A — the doors (the parts that touch the server)
1Clearable event tags revises decision 0027
  • You can now un-set a tag. An event's category, class, and term become clearable — pick "No category" / "School-wide" / empty and it actually clears, so a mistake is fixable in place (no delete-and-recreate). Under the hood: a careful three-state rule — left alone = unchanged, explicitly emptied = cleared, set = set — so nothing clears by accident. Documented as a small revision to the locked 0027 convention.
  • Stop auto-tagging as "Other". Creating an event no longer silently pre-picks the "Other" category — a new event starts genuinely uncategorized unless you choose one.
3Classes at CSV scale — both ways
  • A "class" column in the student CSV. Add an optional third column to the import and each student is auto-created into that class (classes made on the fly by name) — one upload onboards a whole school with its classes. A CSV without the column works exactly as today.
  • A "paste emails" box on a class page. Paste a list of student emails and they're all assigned to that class at once — with a clear "these N were added, these emails didn't match" result. No more 800 clicks.
Sub-phase B — the sweep (front-end only: batch work survives errors)
2The CSV error loop front-end only
  • See problems before you submit. The import preview flags duplicate and clearly-invalid rows up front (instead of you discovering them only in the results).
  • "Download skipped rows". After an import, export the rows that didn't import as a CSV — fix the typos and re-import, with no hand-transcribing.
4Honest downloads front-end only
  • Tell the truth about a partial download. The staff "Download all" gets the same honest messages the student page already uses — "saved N of M" when some fail, the browser-cap notice when it applies, and silence when you simply cancelled the save dialog (instead of a false "success").
5The residue front-end only
  • New teacher appears instantly. Adding a teacher now refreshes the staff list on the spot (today it only shows after a reload).
  • "Who hasn't opened?" in one click. The notify roster collapses behind its summary and gains a "Not opened" filter, so the students who need a nudge surface immediately instead of being scanned for by eye.
A note on the one risky bit: the clearable-tags change (A·1) revises a rule that was deliberately locked (decision 0027, "emptying a field leaves it unchanged"). We scope the change to the three tag fields only and use a careful three-state rule so a field is never cleared or kept by accident — the two review passes will verify that truth table before it ships.

How we'll work

Two sub-phases, each brought back to you. A (the doors) lands first — the server change + its screens — then the full check (server: format + types + tests + the layering rule, on a throwaway database; app: types + lint + build) and a 2× self-review, then to you. Then B (the front-end sweep) the same way. Nothing is committed until you say so. No database migration, no ML change, no new dependency.

How we'll check it

The full gate stays green each sub-phase, plus a walk: clear an event's category / class / term and confirm it sticks (and that leaving a field alone doesn't change it); a new event starts uncategorized; a CSV with a class column creates + assigns; a paste-emails box adds a batch and names the unmatched; the preview flags a duplicate/typo and "download skipped rows" re-imports cleanly; a partial staff download reads honestly and a cancelled one stays silent; a newly-added teacher appears immediately; the roster filters to "Not opened".

Not in this build (noted honestly): undo-toasts for deleting a student/class/category (confirm-first stays — BP18 already removed the worst consequence); true server-side pagination of the roster (the collapse + filter is enough at real scale); clearing an event's description/date (nobody asked — only the three tag fields become clearable). No database change, no ML change, no new permission, no new dependency.
