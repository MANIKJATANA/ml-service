1. What we're building, in plain words

On a student (or an event's By-student view), staff pick some photos — or hit Select all — and press Send on WhatsApp. The system looks up the student's mobile number, and sends each photo straight into their WhatsApp chat, one after another, automatically. A little progress bar shows "Sent 18 of 20", and a summary confirms it. Nothing is downloaded or attached by hand.

2. How it's built (the pieces)

# Frontend (staff) Student detail / By-student tab ──► Select photos + "Send on WhatsApp" # Backend Route POST /v1/students/{id}/whatsapp-send { media_ids[] } │ ├─► WhatsAppShareService # orchestrates one student's send │ ├─ reads student.mobile_number (+ checks opt-in) │ ├─ for each photo: mint short-lived signed URL (existing download mint) │ │ + compress to ≤5 MB WhatsApp variant (Pillow, from BP17) │ ├─ reads the SCHOOL's channel/number (school_whatsapp_config) │ └─ sends via WhatsAppSender port (one media-template per photo) │ ├─► WhatsAppSender port ──► adapter: gupshup | wati | fake(dev) │ (one PLATFORM api key, from settings/env) └─► records each send in whatsapp_send_log (who / to / status)

New backend pieces

  • WhatsAppSender port + a provider adapter (Gupshup or Wati) + a fake/log adapter for dev — the ML-service's ports/adapters pattern, so we can swap providers by config. The provider API key is one platform secret (settings/env), not per-school.
  • WhatsAppShareService — orchestrates a single student's send: number + opt-in check → per-photo signed URL + compress → send N media-template messages via the school's channel → record. Not the BP4 notifier (that's PII-free/best-effort; this needs the number, media & per-message result).
  • school_whatsapp_config table — one row per school: enabled, sender_channel/number (nullable → the shared app number), opt-in policy. No secret columns (the key is platform-level).
  • whatsapp_send_log — append-only (like download_audit): actor, student, count, per-photo status. Trust + debugging.
  • Student mobile_number (Phase 0 dependency) + an opt-in flag/consent per student.

New frontend pieces

  • "Send on WhatsApp" on the student detail (beside the BP26 Download-all) + on the event gallery By-student tab.
  • Reuse the existing select mode (BP13/BP30 selectionMode) + Select-all → the media-id list to send.
  • A send hook (bounded-concurrency pool + progress, like useMediaUpload) → progress "Sent X of N" + an honest summary toast.
  • A (school)/settings WhatsApp screen (new route) — turn it on, pick/confirm the sender number, see opt-in status. (School-admin only — new permission.)

3. WhatsApp's rules we must honour

These are Meta's platform rules (true for any official API / provider) — they shape the build:

Message templates. To send a photo to a student who hasn't messaged the school first, each message must be a Meta-pre-approved template. We approve one template once — an image header + a short caption (e.g. "📸 A photo from {{event}} — {{school}}") — and send it N times with N different photo URLs. So auto-send works with zero manual steps; the approval is a one-time setup per provider/number.
Opt-in. WhatsApp policy requires students to have opted in to hear from the school. We track a per-student consent (collected at enrollment / via the CSV) and only send to opted-in students — the Send button is disabled / warns otherwise. Protects the school's number quality-rating from spam reports.
Signed URLs just work. WhatsApp fetches the image at send time from a public URL — our Supabase signed download URLs (valid ~1 hr) are exactly that, so buckets stay private and we mint a fresh link per send.
5 MB cap + rate/quality. Images must be ≤5 MB → we send a compressed ~2000px variant (Pillow, reusing BP17). Sending 30 messages to one student in a burst also brushes rate/quality limits → the send pool is throttled, and a new number starts on a low daily tier that rises with good standing.

4. Cost & scale (it's our bill now)

Inline = one billed message per photo (utility template, ~₹0.12–0.22 in India). Since the platform pays, this is real spend that scales with students × photos:

Event sizeMessagesApprox cost / event (we pay)
30-student class, ~20 photos each~600₹90 – ₹130
200-student grade, ~15 photos each~3,000₹450 – ₹660
800-student school, ~15 photos each~12,000₹1,800 – ₹2,600
Levers we build in from day one (so cost is controllable even with inline): a per-school monthly message budget/cap, a confirm dialog on large sends ("Send 600 messages?"), the send log for spend visibility, and opt-in gating (never pay to message someone who'll report spam). Marketing-category templates cost ~5× utility — we design the template to qualify as utility/transactional ("here are your photos") to stay on the cheap tier.

5. Build phases (sliced, approve-before-commit)

0  Student mobile number + opt-in dependency

Migration 0021: students.mobile_number (nullable) + a whatsapp_opt_in flag. Threaded through model → DTOs → service → CSV → the create/detail/bulk forms; shown on detail + roster + By-student. Loose phone validation, optional, not unique.

Effort Small · BE + FE · no ML, no new dep. Unblocks everything below.

W1  Provider foundation + per-school settings core

  • The WhatsAppSender port + one provider adapter (Gupshup/Wati) + a fake for dev; the platform API key in settings/.env.example.
  • school_whatsapp_config table + a (school)/settings WhatsApp screen (enable, sender number [default shared], opt-in view) behind a new school-admin permission.
  • The one-time media-template (approved with the provider) + the ≤5 MB compressed variant (Pillow, from BP17).
Effort Medium · BE-heavy + FE settings · new dep = the provider SDK/HTTP · a migration.

W2  The send flow the feature

  • POST /v1/students/{id}/whatsapp-send { media_ids } → WhatsAppShareService (opt-in gate, per-photo signed URL + compress + send, throttled pool, best-effort per photo).
  • FE "Send on WhatsApp" on student detail + By-student tab, reusing select-mode + Select-all; a progress hook + honest summary ("Sent 20 of 20 · 1 failed, retry").
  • The whatsapp_send_log + a large-send confirm + the per-school budget cap.
Effort Medium · BE + FE · reuses the download mint + BP13/BP30 selection.

W3  Scale & polish later

  • "Send to all matched students" for a whole event — this needs a background job/queue (12,000 messages can't run in a request), delivery receipts + retries.
  • Per-school sender numbers (provision a number per school under our provider account) once a school wants its own identity.
  • Delivery-status webhooks (sent/delivered/read) surfaced on the send log.
Effort Medium–Large · a worker/queue · gated on real demand.

6. Security & safety

  • One platform secret, not per-school tokens — the provider API key lives in settings/env (never in the DB, never logged), the honoured "never store secrets in code" rule. Per-school config holds only a channel/number (non-secret).
  • Opt-in gated — never message a student who hasn't consented; the log records every send for accountability (mirrors the BP8b download audit).
  • Tenant-scoped — a school can only send to its own students, number from the token; the mint entitlement is the same one staff already hold.
  • Cost guardrails — per-school budget cap + a large-send confirm so a mis-click can't fire 10,000 paid messages.
