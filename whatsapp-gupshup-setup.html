WhatsApp (Gupshup) — Setup & Go-Live

The step-by-step to turn on real WhatsApp photo delivery

You do — create a Gupshup account, get a WhatsApp Business number, and get one message template approved (Steps 1–3). ~30–60 min of clicking, plus waiting on Meta's template approval (minutes to a day).

The app already has — the settings screen, the per-student "Send on WhatsApp" button, the ≤5 MB image handling, the 12,000/school/month budget cap, opt-in + audit logging. Everything runs on a built-in fake sender today (nothing goes out); this guide flips it to live Gupshup.

✅ Adapter status — good news

The Gupshup adapter in the code has already been confirmed against Gupshup's current public docs — the endpoint, the apikey auth, the form fields, the template + image-header payload, and the response shape all match Gupshup's self-serve WhatsApp API.

The one thing you must get right: the Template ID you paste into the settings screen must be the template's UUID from Gupshup (e.g. c6aecef6-bcb0-4fb1-8100-28c094e3bc6b), not its display name — see Steps 3 & 6.

The only thing that can't be tested without your live account is real delivery. So once your key is set + a template approved, ping me and I'll walk the smoke test with you (and patch anything the live API surprises us with). A first-attempt error is possible — that's just the signal to look at the exact response together.

Prerequisites

  • A business (Gupshup/Meta ask for a business name + basic details).
  • A phone number that is NOT currently on the WhatsApp or WhatsApp Business consumer app — it becomes your sending number and must be free to register to a WhatsApp Business Account (WABA). A cheap dedicated SIM / virtual number works.
  • Access to the backend's .env file (you edit it; it's gitignored — never commit real secrets).

The setup

1 Create a Gupshup account + a WhatsApp app

  1. Sign up at gupshup.io and log in.
  2. Create a new WhatsApp app/channel (Gupshup's "WhatsApp API" product). Give it a name — this becomes your app name (the adapter sends it as the message source src.name).
  3. Keep the dashboard open — you'll come back for the API key and the number.
Tip

Gupshup offers a sandbox for quick testing to your own opted-in number before a real number/template is fully live. Handy for a first smoke — but real business-initiated photo messages need an approved template + a registered number (Steps 2–3).

2 Get a WhatsApp Business number

  1. In the dashboard, start the "go live" / onboard a number flow — Gupshup walks you through creating/linking a WhatsApp Business Account (WABA) via Meta and registering your phone number to it.
  2. Complete Meta business verification if prompted (raises your daily limits; a number can start at a lower tier without it).
  3. Note the number in E.164 digits only — no +, spaces, or dashes — e.g. 919812345678 (India) or 15551234567 (US). This is your sender number.

3 Create + submit ONE message template

Business-initiated messages ("here are your photos") require a pre-approved template. Create exactly one:

  • Category: Utility (transactional) — not Marketing. Utility is cheaper and approves faster.
  • Header: Media → Image — this carries each inline photo (the app fills in a fresh image link per photo at send time).
  • Body: keep it minimal so it approves fast — either fully static (e.g. "Here are your event photos.") or one/two variables. Fewer variables = faster approval. (The app currently sends the template with no body variables, so a static body is the safest first template.)
  • Buttons: none.
⚠️ Copy the template ID, not the name

Once approved, copy the template's ID — a UUID (e.g. c6aecef6-bcb0-4fb1-8100-28c094e3bc6b), shown next to the template in the Gupshup template manager. You paste this ID (not the display name) into the app — Gupshup matches the send by template UUID, so the name won't work.

4 Get your API key

In the Gupshup dashboard, find your API key (account-level or per-app). Treat it as a secret — it goes only in .env, never in code, chat, or a commit.

5 Configure the backend (.env)

Edit the backend .env (same file as BE_DATABASE_URL etc.):

# Flip the provider from the built-in fake to real Gupshup:
BE_WHATSAPP_SENDER_IMPL=gupshup

# The ONE platform secret (Step 4) — never commit this:
BE_WHATSAPP_API_KEY=<your-gupshup-api-key>

# Gupshup API base + your app name (Step 1):
BE_WHATSAPP_BASE_URL=https://api.gupshup.io
BE_WHATSAPP_APP_NAME=<your-gupshup-app-name>

# The shared sender number (Step 2), E.164 digits only.
# A school can override this in its settings screen.
BE_WHATSAPP_DEFAULT_SENDER_NUMBER=<e.g. 919812345678>

# (Optional — sane defaults already exist)
BE_WHATSAPP_MONTHLY_SEND_CAP=12000     # per school, per month
BE_WHATSAPP_IMAGE_MAX_BYTES=4800000    # keep each photo under 5 MB

Then restart the backend so it picks up the new values.

6 Configure WhatsApp (in the app, as the platform admin)

Schools no longer configure WhatsApp — the platform admin owns it all (0099). Sign in as the platform admin → WhatsApp in the left nav (/whatsapp):

  1. Sender number — the Gupshup source number you registered (for Meta, the phone-number ID).
  2. Meta access token — only for the Meta provider (leave blank for Gupshup — its key is in .env).
  3. Template name — paste the approved template's UUID from Step 3 for Gupshup (e.g. c6aecef6-bcb0-4fb1-8100-28c094e3bc6b, not the display name), or the template's name for Meta. A send fails until this is set.
  4. Interim test number — optional; while set, every "Send on WhatsApp" diverts to it (testing).
  5. Save. No restart — the DB values apply on the next send.

7 Prepare a test student (opt-in + number)

The app only sends to a student who is opted in and has a mobile number:

  1. Open a student's detail page → the WhatsApp row → Edit.
  2. Set the mobile number to your own WhatsApp number (E.164, e.g. +91…) for the test.
  3. Check "Opted in to WhatsApp messages" → Save.
Tip

For the very first test, message your business number from your own phone first (or use Gupshup's sandbox opt-in) so your number is a known contact — avoids delivery being blocked for lack of consent.

8 The live smoke test

  1. Make sure your test student appears in at least one photo (enrolled + an event with their photo processed) — the "Send on WhatsApp" button is in their "Appears in" section (and on the event gallery By student tab).
  2. Click "Send N on WhatsApp" → the confirm dialog shows the exact cost → Send.
  3. Expected success: the message(s) arrive on your WhatsApp (one image per photo); the toast reads "Sent N of N."; a send-log row is written per photo with a provider message id.
  4. If it fails (a 502 / "failed"): send me the error and I'll verify/patch the Gupshup call against the live docs.

Known v1 limits

  • No auto re-try dedupe: re-sending after a partial failure re-sends the photos that already went (and re-bills them). The button is disabled while a send is in flight, so no accidental double-clicks.
  • Send is per-student (pick a student, send their photos). "Send to everyone in an event" is a future phase (W3c).
  • Compressed image copies aren't auto-deleted — run the cleanup CLI periodically (python -m backend.cli.reap_whatsapp_variants); a compose comment documents it.

Alternative: Meta WhatsApp Cloud API (instead of Gupshup)

You can send directly through Meta's WhatsApp Cloud API — your own WhatsApp Business account, no BSP in the middle — by switching one env var. Everything else (settings screen, Send button, opt-in, budget cap) is identical; only the credentials + the template field differ.

Set up once:

  1. Create a Meta WhatsApp Business account (business.facebook.com / developers.facebook.com).
  2. Add/register a phone number → note its Phone number ID (this is your sender).
  3. Generate a permanent / system-user access token (a short-lived dev token expires — don't use it in production).
  4. Create + get approved a template with an Image header + a minimal body → note its name.

Configure .env: only the provider selector + non-secret Graph API plumbing live in .env.

BE_WHATSAPP_SENDER_IMPL=meta
BE_WHATSAPP_META_API_VERSION=v21.0                     # keep current
BE_WHATSAPP_META_TEMPLATE_LANG=en_US

The access token and the sender phone-number ID are NOT env vars — set them in the UI at Platform → WhatsApp (DB-only, resolved fresh per send, no restart). On that same screen the Template name field takes the approved template's name for Meta (Meta matches by name, not a UUID).

Differences vs Gupshup

Meta matches a template by its name (Gupshup uses the UUID) — paste the right value in the Template name field at Platform → WhatsApp (its hint spells out which per provider). For Meta the "Sender number" field IS the Meta sender phone-number ID; for Gupshup it's the source number. Keep the API version current — Meta deprecates old Graph versions.

Four DB-controlled fields (no restart) + interim test mode

Meta's temporary token expires ~daily. Instead of editing .env + restarting, go to Platform → WhatsApp — that one screen has four fields, all stored in the DB and applied on the next send (schools no longer configure WhatsApp, 0099):

  1. Sender number — the Meta sender phone-number ID (from Meta → WhatsApp → API Setup, the numeric "Phone number ID", not the +country number). This is the ONLY place it's set — there is no env var for it.
  2. Meta access token — paste a fresh token; stored only in the DB (no env var), never shown again (only "set · ending 1234").
  3. Template name — the approved template's name (Meta) or UUID (Gupshup). A real (non-interim) send fails until this is set.
  4. Interim test number — the pre-template test mode. Setting a number here turns it ON (there is no separate toggle): "Send on WhatsApp" then sends a text + the real photos to that number, not the student. It only delivers inside WhatsApp's 24-hour window, and it diverts all sends while set — clear the field for normal delivery.
