📱 Student mobile numbers + per-school WhatsApp

A code-grounded exploration of two owner asks: (1) store a mobile number for every student and show it where it matters, and (2) let each school run its own WhatsApp to send students their photos. Researched with 4 parallel agents — 2 mapping our codebase, 2 on the live WhatsApp landscape (2026).

A. Student mobile number — the plan

Add a nullable mobile_number to each student, threaded through every layer and shown where staff act on a student. It's the contact you'd message on WhatsApp, so it must land first.

Backend (the model)

  • Migration 0021 (latest is 0020): add students.mobile_number — nullable text, no index, no unique constraint, no backfill. Mirrors reference_photo_path exactly.
  • One read chokepoint: add mobile_number to _to_student() in the postgres adapter and it flows out of every read at once (get / list / by-ids / by-emails).
  • Student domain dataclass gains mobile_number: str | None = None (frozen — added last so every existing constructor still works).
  • DTOs: CreateStudentRequest, StudentResponse (→ StudentListItem free), BulkStudentRow each get the field (max_length=32).

Backend (the writes)

  • create_student / _provision_student / bulk_create_students thread the number through.
  • Editing: a new PATCH /v1/students/{id}/mobile → set_mobile_number() (tenant-scoped, 404-before-write) — mirrors the existing set_status. Cleaner than overloading the class-only PATCH.
  • Validation: a small new domain/phones.py (like domain/emails.py) — pragmatic ^\+?[0-9]{7,15}$ after stripping separators. No country-code requirement (staff paste local 10-digit Indian numbers), no libphonenumber dependency.

Frontend — where it's entered & shown

Enter
  • Create-student dialog (tel input)
  • Student detail — inline edit
  • Bulk CSV: header-detected mobile/phone column (back-compatible)
Show
  • Student detail profile (primary)
  • Notify roster WhatsApp-useful
  • Event gallery "By student" WhatsApp-useful
Defaults
  • Optional / nullable
  • Not unique, no index
  • Off the main list (detail-only)

Effort: small & self-contained — one migration + a field threaded through the layers you already know (it's the exact shape of email / reference_photo_path). No ML, no new dependency.

B. WhatsApp: the 4 ways to actually send photos

There are only four real ways to get a photo into a student's WhatsApp. They split into two worlds: a human presses send (free, manual) vs the server sends (automated, but regulated + paid).

ApproachSend photos?Template needed?Opt-in / 24h ruleCostSetupBan risk

2. BSP
Gupshup, Wati, 360dialog, Twilio…		 Yes (wraps Cloud API) Same rules Same rules Meta fee + markup / monthly Lower (hosted) Low
3. wa.me / share-sheet
no API — a human sends		 Text link only; media via manual attach / OS share-sheet None None Free Trivial None
4. Unofficial libs
whatsapp-web.js, Baileys		 Yes None None "Free" + infra Medium HIGH — ToS breach, permanent ban
Rule out #4. Unofficial automation (driving a real WhatsApp Web session) violates WhatsApp's ToS — the number can be banned permanently and unpredictably, taking down delivery for every school on it. Never for a production, multi-tenant product.
What sending N photos really costs. Cloud API sends one image per message — no albums. So a student's 30 photos = 30 messages. Pricing went per-message in Jul 2025. The lever: send one approved template to open, then push the rest as free-form images inside the 24-hour window (free today) — but that window only opens when the student replies. And from Oct 1 2026 Meta begins charging in-window messages too. Budget realistically as N × the template rate.
Good news for our storage. A WhatsApp image can be sent by public link — WhatsApp fetches it at send time. Our Supabase signed download URLs (valid ~1 hr, inline-served) work as that link, so buckets stay private and we mint a short-lived link per send. One catch: the 5 MB image cap — high-res event photos may exceed it, so we'd send a compressed ~2000px variant (our BP17 thumbnail machinery already resizes).

C. "Each school does their own" — 4 models, ranked

The owner's core requirement: WhatsApp is per-school. Here's how a SaaS lets each tenant connect its own WhatsApp, ranked for a small team + non-technical schools.

1 wa.me / share-sheet ship as v1

Staff download the student's photos (we already built per-student "Download all"), then share them into WhatsApp via the phone's share-sheet, or tap a wa.me/<number> link that opens a chat with a prefilled caption — and attach the photos.

School onboarding
None — uses whatever WhatsApp is on staff phones.
Platform holds
No credentials. Nothing in our DB.
Cost
Free — regular WhatsApp, no API fee.
  • Literally satisfies "each school runs its own WhatsApp" — each uses its own number.
  • No secrets to protect, no Meta approval, no template/opt-in regime.
  • Only limit: manual (staff attaches the photos). wa.me can't pre-attach media — the share-sheet can push the actual files.

2 Meta Tech Provider + Embedded Signup the real v2

We register once as a Meta Tech Provider. Each school clicks "Connect WhatsApp" → a Meta popup opens → they log in with their Facebook Business account, create/select their own WhatsApp Business Account (WABA) + phone number, verify it. We get back a per-school token scoped to that school, and send on their behalf.

School onboarding
Moderate — guided popup, but needs an FB Business account + a fresh number + a payment method.
Platform holds
Per-school waba_id + phone_number_id + a scoped business-integration token.
Cost
School pays Meta directly per conversation.
The real work: a Meta Business app + App Review (whatsapp_business_messaging/_management) + Business Verification + Tech Provider verification (capped at ~10 schools/week until verified, then ~200), the Embedded-Signup JS + server code-exchange + webhooks, KMS-encrypted per-school token storage, and — the sleeper cost — building template creation/approval + student opt-in. This is a project, not a feature.

3 BSP reseller v2 shortcut

A provider (360dialog, Twilio, Gupshup) wraps the Meta plumbing. Each school connects its WABA under our partner/sub-account; we hold a scoped BSP channel key (not raw Meta tokens — smaller blast radius).

  • Build: Medium — the BSP absorbs Meta App Review.
  • Cost: per-channel monthly fees × N schools; we become the biller.
  • India-native BSPs (Gupshup/Wati/Interakt) fit the market; 360dialog for near-pass-through pricing.

4 BYO credentials avoid (for now)

Each school does the entire Meta setup themselves and pastes a permanent token + phone-number-id into our settings.

  • ✕ Developer-grade setup — non-technical schools can't do it unaided.
  • ✕ A permanent, full-scope token per school sitting in our DB — the worst credential to hold.
  • ✓ Only merit: lowest platform build. Fine only if buyers are technical.

D. The catch that makes the API a real project

You cannot freely message a student who hasn't messaged you first. WhatsApp's rules for any API path (models 1–3):

  • Opt-in — the student must have opted in to hear from the school.
  • 24-hour window — free-form messages (the actual photos) are only allowed inside a 24h window that opens when the student messages the school.
  • Templates — to start a conversation (outside a window), you must send a Meta-pre-approved template. A template header can carry one image, so the first photo can ride along; the rest go free-form once the window is open.

This is why "store a token and POST a photo" understates the API path by a lot — it's really token management + opt-in capture + template design/approval + the 24h-window dance. The wa.me v1 has none of this (a human on consumer WhatsApp isn't bound by the Business API rules), which is a second strong reason to ship it first.

E. How it plugs into our system

Our codebase is greenfield for this — no wa.me/share/WhatsApp anywhere today. Here's the clean fit (from mapping the actual ports & flows).

The send flow (v2, per-school API)

1 · Staff picks a student
Student detail "Appears in" (beside the BP26 Download-all) — the primary trigger. Event gallery "By student" is secondary.
2 · System gathers
the student's mobile_number + their effective photos → mints short-lived Supabase signed URLs (the existing download mint).
3 · New WhatsAppSender port
a WhatsAppShareService reads the school's WhatsApp config and sends via that channel. Not the BP4 NotificationChannel (that seam is PII-free / best-effort / fire-and-forget — a real send needs the number, media & delivery feedback).

Where per-school config lives

  • New school_whatsapp_config table — one row per school, the access token / BSP key in an encrypted column.
  • New (school)/settings route (we have none today) + a new school-admin permission — the existing PATCH /schools is platform-only.
  • Security bar if we hold tokens: envelope encryption + KMS, per-tenant key isolation, never log the token, one-click revoke/reconnect. (The BSP model shrinks the blast radius; the wa.me v1 holds nothing.)
The v1 bridge is tiny. A "Send on WhatsApp" button on the student detail that opens https://wa.me/<mobile_number>?text=<prefilled caption> (or the share-sheet with the downloaded files) needs only students.mobile_number — no new table, no token, no permission, no backend send path, no Meta account. It's the honest first step and it's essentially Phase 0 + a button.

F. Phased roadmap

0  Student mobile number dependency

Migration 0021 + the field threaded through model → DTOs → service → CSV → the create/detail/bulk forms, shown on detail + roster + by-student. Loose validation, optional, not unique.

Effort: Small. Backend + Frontend. No ML, no new dependency. Unblocks both v1 and v2.

1  wa.me "Send on WhatsApp" ship first

A per-student "Send on WhatsApp" affordance: opens wa.me/<number> with a prefilled caption, and/or the OS share-sheet pre-loaded with the just-downloaded photos. Staff sends from their own (school's) WhatsApp.

Effort: Small (FE-mostly). No backend send path, no secrets, no cost, no Meta. Honest limit: manual attach; iOS share-sheet UX varies.

2  Real per-school API when demanded

Automated sending. Choose the connect model — Embedded Signup (Tech Provider) for the cleanest "school owns it + pays Meta", or a BSP to skip Meta App Review for a per-channel fee. Adds: school_whatsapp_config (encrypted), a (school)/settings connect flow, the WhatsAppSender port + service, template/opt-in handling, and a compressed ≤5 MB image variant.

Effort: Large. Backend-heavy + external approvals + ongoing token security. Gated on real demand for automation. Decide Embedded-Signup vs BSP at that time.
